# Technical report: reading CVs and ranking candidates, measured

This is the long version of the README: what the system does, why it is built
the way it is, what was measured, what did not work, and what is still not
known. Every number links to the script and report that produced it. The data
behind almost all of them is synthetic and generated by this repository, so the
numbers describe behaviour under the noise and layouts the generators model; they
are not hiring accuracy.

## 1. The problem and the constraints

A recruiter receives CVs as PDFs and Word files in many layouts (one or two
columns, sidebars, timelines), languages and fields, and has to find the people who
fit a job. The system reads each CV into a structured profile, indexes it, and ranks
candidates for a job (or jobs for a candidate) with a score that can be explained.

The constraints shaped most decisions:

- **CPU only.** The language model is a 7B model in GGUF form on a CPU. One CV
  that needs it takes minutes, so the model is the last resort, not the default.
- **No labelled real data.** There is no set of CVs with known correct profiles
  or known good hires. Quality is measured on generated CVs whose true content is
  known by construction, plus nine real CVs labelled by an AI assistant and not yet checked by a person.
- **Personal data.** CVs carry names, contact details and, in text, instructions
  aimed at the model. Logs are redacted, reports hold aggregates only, and CV text
  is treated as untrusted input.

## 2. How it works

```text
upload ─► validation ─► queue (database) ─► worker threads
                                              │
   PDF / DOCX / image ─► parse ─► layout (blocks, columns, regions)
                                              │
                          section detection (heading words → look → classifier → model)
                                              │
                          extraction (rules first, model when unclear) + NER + skills
                                              │
                          confidence score ─► MongoDB profile ─► embedding ─► FAISS
job text ─► same extraction ─► hybrid score (skills, meaning, experience) ─► explained ranking
```

Details by area: [architecture and API](api.md), [deployment and platform](platform.md),
[vocabulary files](vocabulary.md), [evaluation index](evaluation/README.md).

## 3. Decisions, and the evidence behind them

**Rules first, model second.** Regular sections (jobs, schools, summaries,
certificates, projects) are read by rule parsers whose word lists are JSON data;
the model is asked only when a layout cannot be split into role and company. On
four synthetic CVs this took extraction from 407 s to 42 s per CV on CPU and found
the companies, roles and degrees the slow path missed
([extraction speed](evaluation/extraction_speed_README.md)). The price is
brittleness on real layouts: on the nine real CVs the rules read little of the
experience sections, and most of them still go to the model
([real CVs](evaluation/real_cv_README.md)).

**Section detection by layers.** A heading is recognised by its words, then by
its look relative to the CV's own known headings, then by an embedding classifier,
and only unfamiliar headings are put to the model, once, with the answer cached.
Line accuracy on 144 generated CVs (6 industries, 6 layouts, 2 languages) is 0.978
with the model answering unfamiliar headings and 0.860 without it; adding each layer
raised the score on headings the lexicon was not built around from 0.573 to 0.783
([section detection](evaluation/section_detection_README.md)). The lexicon and the
corpora were written by the same hand; the "industry" wording was chosen to differ
from what the lexicon was built around, and the report says so.

**Hybrid scoring, not one model.** The score combines skill coverage, semantic
similarity of profile and job text, and experience (when the job states a
requirement). On 300 candidates and 30 jobs the hybrid scorer reaches nDCG@10 0.894
against 0.784 for BM25 on labels that depend on role family and seniority, with
paired bootstrap intervals; on labels that depend on the family alone BM25 is
indistinguishable from it ([synthetic evaluation](evaluation/synthetic_v1.md)). Labels are
generated from latent attributes, never from the skills a candidate lists, so a
skill-overlap ranker is not scored against labels it defines.

**Word files are read by simulating a page.** A `.docx` has no coordinates, but
every later stage needs them. The parser stacks paragraphs on a virtual page,
applies styles through the style chain, places table cells as columns and text boxes
at their anchors. It is checked at 1.000 on generated Word versions of the corpus,
and said not to be evidence about real Word files ([docx parsing](evaluation/docx_parsing.md)).

**A confidence score per CV.** The pipeline records how each section was found,
who answered each extractor, and whether the text came from OCR, and turns that into
a score with reasons. It separates empty or visibly broken extractions from good ones
(rank correlation with accuracy 0.65 on 120 synthetic CVs, 0.91 on 9 real ones) and
cannot detect a plausible but wrong entry; the threshold for "high" was chosen after
seeing the data and is flagged as such ([confidence](evaluation/confidence.md)).

**A queue in the database instead of Celery.** Uploads wait as `pending`
resumes; workers claim them atomically with a lease, retry temporary failures with
a growing delay, and give up on a CV that keeps killing its worker. It needs no new
service and is tested against an in-memory and a real MongoDB. The cost: the
workers must live in the API process because the vector index is in its memory
([platform](platform.md)).

**A CI gate on quality.** Besides unit tests, CI re-runs small fixed evaluations
and fails when ranking or section accuracy fall by more than 0.02 or when a pronoun
or a name changes a score ([eval_gate.py](../scripts/eval_gate.py)).

## 4. How the measurements are kept honest

- Synthetic corpora have known truth; relevance labels come from latent attributes
  and not from the text a ranker reads.
- Differences are reported with bootstrap intervals over jobs or CVs, and paired when
  the same jobs are ranked by different systems. Groups of fewer than three CVs are
  not reported separately.
- Choices are made on one dataset and reported on another: the reranker's blend
  weight was to be picked on a development set (30 jobs) and reported on a fresh one
  (60 jobs, other seed).
- Every report states what it cannot show next to the number.
- Real CVs and their labels never leave the machine; published reports hold
  aggregates only.

## 5. What did not work, or turned out different

- **Reranking with a cross-encoder lowered quality at every blend weight** (nDCG@10
  0.880 → 0.855 at the lightest, 0.707 alone). It is built, tested and off by default
  ([ranking quality](evaluation/ranking_quality.md)). A model trained on resume-job pairs,
  or real CV prose, might behave differently; neither was available.
- **Rules are far weaker on real CVs than on generated ones.** Core entity F1 is 0.62
  with the model and 0.48 without it on nine real CVs, against near-perfect results on
  generated ones. Generated CVs are cleaner than real ones; this gap is the main reason
  the real-CV benchmark exists.
- **BM25 matches the hybrid scorer** on labels that depend on role family alone. The
  hybrid advantage is the experience signal.
- **Skills extraction** has recall 0.33 to 0.47 and precision near 0.1 on real CVs
  because the taxonomy returns skills a person would not list. Unchanged.
- **Column placement of headingless regions** (a fix for designed templates) moved
  real-CV entity F1 from 0.455 to 0.482, inside the interval: a small gain on one layout
  family, not a general improvement.

## 6. What measuring found that reading the code did not

- A name, a pronoun or a language change in the profile moved the match score of up to
  half the candidates, because the embedding reads every word. Removing pronouns, titles
  and the person's own name from the embedded text brought the shift to exactly zero
  ([fairness audit](evaluation/ranking_quality.md)). A women-in-engineering line (selection
  ratio 0.87) and a CV in Vietnamese against an English job (0.91) still score slightly
  lower.
- The first call to the jobs endpoints took 71 seconds (services built lazily); a start-up
  warm-up fixed it. Embedding the job text was 117 of 180 ms per match; an LRU cache removed it
  for jobs matched again ([load test](evaluation/load_test.md)).
- Removing "Additional Information" from the heading lexicon recovered the skills of
  50 of 78 real files (copies of a few CVs): the heading says nothing about what is under it.

## 7. Limitations that matter

- Everything quantitative is synthetic except nine real CVs, labelled by an AI assistant
  and not yet by a person; most of them are public samples and templates.
- The French, Spanish, German, Portuguese and Russian vocabulary was checked on fifteen CVs
  written by the author of the vocabulary files.
- OCR was not run (no Tesseract on the development machine); image uploads are tested up to
  the conversion to a page.
- One process: the vector index and the models are in memory. Scaling out needs a shared
  vector store and a queue consumer elsewhere.
- Fairness was audited only with synthetic counterfactual pairs of the changes someone
  thought of.
- Scores order candidates for a person to read. They are not a judgement of ability and
  should not be used to reject anyone.

## 8. Reproducing it

| To get | Run |
|---|---|
| ranking report | `python -m scripts.run_evaluation --dataset data/evaluation/synthetic_v1 --out docs/evaluation/synthetic_v1.md` |
| section detection | `python -m scripts.evaluate_sections` |
| extraction speed | `python -m scripts.benchmark_extraction --documents 4` (needs the GGUF model) |
| other languages | `python -m scripts.evaluate_languages` |
| confidence vs accuracy | `python -m scripts.evaluate_confidence` |
| reranking | `python -m scripts.evaluate_reranking --model <cross-encoder>` |
| fairness | `python -m scripts.audit_fairness` |
| load | `python -m scripts.load_test` |
| the CI gate | `python -m scripts.eval_gate` |
| the demo's recorded answers | `python -m scripts.make_demo_fixtures` |
