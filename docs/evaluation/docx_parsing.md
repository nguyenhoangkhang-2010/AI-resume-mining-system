# Reading Word (.docx) CVs

Until this change an uploaded `.docx` passed the upload check (the file starts
with the zip signature) and then failed in the background, because the parser
only knew PDF. The README and the API reference nevertheless said Word was
accepted.

## How a Word file is read

A Word file has no pages or coordinates; the later stages (layout analysis,
columns, section detection by heading style, extraction) need them. The parser
([docx_parser.py](../../app/resume_processing/parsers/docx_parser.py)) therefore builds
the same structure the PDF parser makes, from what Word does store:

| In the Word file | In the layout structure |
|---|---|
| paragraphs, in document order | text blocks stacked down a virtual A4/Letter page |
| run font, size, bold, italic, colour (with the style chain, so "Heading 1" is bold and larger) | span font, size, flags, colour, which heading detection by style uses |
| space before / after a paragraph | the gap between lines, so a spaced heading looks spaced |
| list paragraphs (bullet or numbered) | a visible "• " (Word keeps the symbol out of the text) |
| tables | columns side by side, so a two-column template is read as two columns |
| text boxes (sidebars of designed templates) | blocks at the position they are anchored, read once (the legacy fallback copy is skipped) |
| the first section's header | text above the body (contact details often live there) |
| page breaks and overflowing pages | more pages |
| hyperlinks | their text (an email address is often a link) |

Not read: text inside pictures, footers, comments, tracked deletions and the
old binary `.doc` format.

## Safety

The upload is refused with 400 unless it is a zip that contains
`word/document.xml`, has at most 2,000 entries, unpacks to at most 100 MB and at
most 200 times its size (a zip bomb is a few kilobytes that unpack to gigabytes).
The same check runs again before parsing. XML entities are not resolved by the
Word library. A file that opens but cannot be read ends as `failed` with the
reason `unreadable_file`; the error message, which could hold CV text, is not
stored.

## Measured

Section detection on Word versions of the synthetic CVs (18 CVs, standard
wording, English, no LLM; generated by `tests/test_docx_parser.py`: the same lines
under "Heading 1" titles, bullets as list paragraphs):

| Layout | Line accuracy |
|---|---|
| single column | 1.000 |
| sidebar as a two-column table | 1.000 |

These documents are clean: headings use Word's heading styles and the content is
the corpus text. Real Word CVs vary more (headings typed in bold body text,
layout done with spaces and tabs, text in shapes, images of text). No real Word
CVs were available to measure, so treat these numbers as showing that the
structure is read correctly, not as accuracy on real files; adding a few real
`.docx` files to the real-CV set ([real_cv_README.md](real_cv_README.md)) is the
way to find out.
